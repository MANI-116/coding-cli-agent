Streaming & Real-Time Output

Why streaming matters: The agent makes multiple tool calls before responding. Without streaming, the user stares at a blank terminal for seconds. Streaming shows progress in real time — "Analyzing...", "Executing tool...", partial responses.

// Conceptual streaming integration
async function streamResponse(prompt: string, onChunk: (chunk: string) => void) {
  const stream = await provider.chatStream([{ role: 'user', content: prompt }]);

  for await (const chunk of stream) {
    onChunk(chunk.content); // Updates OutputArea in real time
  }
}

Implementation Plan:

  • Use AsyncIterable from LLM provider SDKs (OpenAI supports streaming natively)
  • Pipe chunks into Ink's useInput / state updates for real-time rendering
  • Show intermediate status updates: "🔍 Searching codebase...", "⚙️ Running tool: readFile"
  • Buffer small chunks and flush periodically for performance

Phase 2 — Agentic Loop (ReAct Pattern)

2.1

Agent Loop Engine

Pattern: ReAct (Reasoning + Acting) — the agent alternates between reasoning about what to do and executing tool calls.

// src/agent/AgentLoop.ts (conceptual)
export class AgentLoop {
  async run(userInput: string): Promise<string> {
    const context = await this.contextBuilder.build(userInput);
    const history = this.memory.getRecentEpisodes(10);

    let done = false;
    let finalResponse = '';

    while (!done) {
      const response = await this.llm.chat([
        { role: 'system', content: this.buildSystemPrompt(context) },
        ...history,
        { role: 'user', content: userInput },
      ]);

      const action = this.responseParser.parseAction(response);

      if (action.type === 'final_answer') {
        finalResponse = action.content;
        done = true;
      } else if (action.type === 'tool_call') {
        const result = await this.toolExecutor.execute(action.toolName, action.args);
        this.memory.addEpisode({ type: 'tool_call', summary: `${action.toolName} -> ${result.status}` });
        // Feed result back to LLM for next reasoning step
        history.push({ role: 'tool', content: JSON.stringify(result), toolCallId: action.id });
      }
    }

    return finalResponse;
  }
}

Loop Flow:

  1. Receive user input → Build context (retrieve relevant code, memory)
  2. Call LLM with system prompt + context + conversation history
  3. Parse LLM response → either tool_call or final_answer
  4. If tool_call → execute tool → feed observation back → go to step 2
  5. If final_answer → return to user
Resources: ReAct Paper (Google DeepMind) — ReAct Prompting Guide

The LLM must respond in a predictable structured format (JSON) so your code can reliably parse tool calls vs final answers.

Phase 3 — Tool Registry & Tool Executor

3.1

Tool Registry (Factory / Service Locator Pattern)

Purpose: Tools register themselves and are resolved dynamically by name. New tools can be added without modifying the agent loop.

// src/tools/registry/ToolRegistry.ts
export class ToolRegistry {
  private tools = new Map<string, Tool>();

  register(tool: Tool): void {
    this.tools.set(tool.name, tool);
  }

  registerMany(tools: Tool[]): void {
    tools.forEach(t => this.register(t));
  }

  get(name: string): Tool {
    const tool = this.tools.get(name);
    if (!tool) throw new Error(`Tool "${name}" not found`);
    return tool;
  }

  getAllDefinitions(): ToolDefinition[] {
    return Array.from(this.tools.values()).map(t => ({
      name: t.name,
      description: t.description,
      inputSchema: t.parameters,
    }));
  }
}

Key Decisions:

  • Dynamic loading: Tools can be loaded from plugins/packages at runtime (useful for user extensions)
  • Registration at startup: Scan a tools/ directory and auto-register
  • Versioning: Each tool can have a version — helpful for updates
Resources: Factory Pattern — Service Locator Pattern
3.2

Tool Executor (Command Pattern)

Pattern: Command — each tool execution is encapsulated as a command object with boundaries (timeout, output limits).

// src/tools/executor/ToolExecutor.ts
export interface ExecutionOptions {
  timeout: number;           // ms (e.g., 30000 = 30s)
  maxOutputBytes: number;    // (e.g., 1MB)
  workingDirectory?: string;
}

export class ToolExecutor {
  constructor(
    private registry: ToolRegistry,
    private options: ExecutionOptions
  ) {}

  async execute(toolName: string, args: Record<string, unknown>): Promise<ToolResult> {
    const tool = this.registry.get(toolName);

    // Pre-execution guardrails
    this.preValidator.validate(tool, args);

    // Execute with timeout via AbortController
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), this.options.timeout);

    try {
      const result = await tool.execute(args);

      // Post-execution guardrails
      this.postValidator.validate(result);

      // Cap output size
      if (this.exceedsMaxSize(result)) {
        result.data = this.truncate(result.data, this.options.maxOutputBytes);
        result.truncated = true;
      }

      return result;
    } catch (error) {
      if (error.name === 'AbortError') {
        return { success: false, error: 'Tool execution timed out' };
      }
      return { success: false, error: error.message };
    } finally {
      clearTimeout(timer);
    }
  }
}

Critical Safety Features:

  • Timeouts: Every tool execution gets an AbortController-based timeout. Prevents infinite loops.
  • Output capping: Limit stdout/stderr to a max size. Prevents memory overflow from noisy commands.
  • Isolation: Run in child_process — not the main thread. A crash in the tool doesn't crash the agent.
Resources: Node.js child_process — AbortController — Command Pattern
3.3

Security & Sandboxing

Two-tier approach:

  • Tier 1 (Default): Spawn child processes with strict boundaries — timeout, output cap, allowed commands whitelist
  • Tier 2 (Future/Enterprise): Docker container sandbox — each tool execution spins up a disposable container
// Example: Whitelist-based shell tool
export class ShellTool implements Tool {
  name = 'execute_shell';
  description = 'Run a shell command';
  parameters = { command: { type: 'string', description: 'The command to run' } };

  private ALLOWED_COMMANDS = ['ls', 'cat', 'grep', 'find', 'node', 'npm', 'git'];

  async execute(args: { command: string }): Promise<ToolResult> {
    const baseCmd = args.command.split(' ')[0];
    if (!this.ALLOWED_COMMANDS.includes(baseCmd)) {
      return { success: false, error: `Command "${baseCmd}" is not allowed` };
    }

    // Spawn child process with timeout
    const { exec } = require('child_process');
    return new Promise((resolve) => {
      const proc = exec(args.command, { timeout: 10000, maxBuffer: 1024 * 1024 },
        (error, stdout, stderr) => {
          if (error) return resolve({ success: false, error: error.message });
          resolve({ success: true, data: stdout });
        }
      );
    });
  }
}

Phase 4 — Context Building & Retrieval

4.1

AST Parsing (TypeScript Compiler API)

Key insight: You don't need an LLM to understand code structure. Use the TypeScript Compiler API (or Babel for JS) to parse code into AST and extract functions, classes, interfaces, and their associated comments.

// src/context/parser/CodeParser.ts (conceptual)
import ts from 'typescript';

export interface CodeChunk {
  id: string;
  filePath: string;
  kind: 'function' | 'class' | 'interface' | 'variable';
  name: string;
  signature: string;
  docComment: string;
  code: string;              // The actual source text
  startLine: number;
  endLine: number;
}

export class CodeParser {
  parseFile(filePath: string): CodeChunk[] {
    const sourceFile = ts.createSourceFile(
      filePath, fs.readFileSync(filePath, 'utf8'),
      ts.ScriptTarget.Latest, true
    );
    const chunks: CodeChunk[] = [];

    ts.forEachChild(sourceFile, node => this.walk(node, chunks, filePath));

    return chunks;
  }

  private walk(node: ts.Node, chunks: CodeChunk[], filePath: string) {
    if (ts.isFunctionDeclaration(node) && node.name) {
      chunks.push({
        id: `${filePath}::${node.name.text}`,
        filePath,
        kind: 'function',
        name: node.name.text,
        signature: node.getText().split('{')[0].trim(),
        docComment: this.getJSDoc(node),
        code: node.getText(),
        startLine: node.getStartLineOfPosition(sourceFile),
        endLine: node.getEndLineOfPosition(sourceFile),
      });
    }
    ts.forEachChild(node, child => this.walk(child, chunks, filePath));
  }
}

What to extract from each chunk:

  • Identifier: Unique ID (filePath + function/class name)
  • Signature: The function/class signature (params, return type)
  • Doc comments: JSDoc or preceding comments
  • Code body: The full source text (for context)
  • Metadata: File path, line range, last modified timestamp
Resources: TypeScript Compiler API — TS AST Viewer (interactive playground) — Babel Parser (for JS projects)

Embeddings Generation

Convert code chunks into vector embeddings for semantic search.

// src/context/embeddings/EmbeddingService.ts
export class EmbeddingService {
  constructor(
    private provider: 'openai' | 'local',
    private model: string = 'text-embedding-3-small' // OpenAI
  ) {}

  async embed(texts: string[]): Promise<number[][]> {
    if (this.provider === 'openai') {
      const resp = await openai.embeddings.create({
        model: this.model,
        input: texts,
      });
      return resp.data.map(d => d.embedding);
    }

    if (this.provider === 'local') {
      // Use sentence-transformers via onnx or local inference
      // HuggingFace's Transformers.js for Node.js
      return this.localEmbed(texts);
    }
  }
}

4.4

Incremental Index Updates

Problem: When a file changes, you can't dump and rebuild the entire index. You need incremental updates.

Solution: Watch for file changes using fs.watch / chokidar, re-parse only the changed file, re-embed changed chunks, and update/delete vectors by ID.

// Incremental update flow
class IndexManager {
  async onFileChange(filePath: string) {
    // 1. Parse only this file
    const newChunks = this.parser.parseFile(filePath);

    // 2. For each chunk, check if it changed (compare hash)
    for (const chunk of newChunks) {
      const existingHash = await this.getStoredHash(chunk.id);
      const newHash = this.hash(chunk.code);

      if (newHash !== existingHash) {
        // 3. Re-embed and update
        const vector = await this.embeddings.embed([chunk.code]);
        await this.vectorStore.update(chunk.id, vector[0], {
          filePath: chunk.filePath,
          name: chunk.name,
          kind: chunk.kind,
          signature: chunk.signature,
          timestamp: Date.now(),
        });
        await this.storeHash(chunk.id, newHash);
      }
    }

    // 4. Handle deletions (chunks removed from file)
    const removedChunks = await this.findRemovedChunks(filePath, newChunks);
    for (const id of removedChunks) {
      await this.vectorStore.delete(id);
    }
  }
}

// src/context/retrieval/Retriever.ts
export class Retriever {
  async retrieve(query: string, topK: number = 10): Promise<RetrievedChunk[]> {
    // 1. Embed the user query
    const queryVector = await this.embeddings.embed([query]);

    // 2. Search vector DB by semantic similarity
    let results = await this.vectorStore.search(queryVector[0], topK * 2); // oversample

    // 3. Apply metadata filters (context cues)
    if (query.match(/frontend|ui|component/i)) {
      results = results.filter(r =>
        r.metadata.filePath?.includes('components/') ||
        r.metadata.filePath?.includes('ui/') ||
        r.metadata.filePath?.endsWith('.tsx')
      );
    }

    if (query.match(/recent|latest|new|last/i)) {
      results = results.sort((a, b) =>
        (b.metadata.timestamp as number) - (a.metadata.timestamp as number)
      );
    }

    // 4. Rank and return top K
    return results.slice(0, topK).map(r => ({
      id: r.id,
      code: this.loadOriginalCode(r.id),
      score: r.score,
      metadata: r.metadata,
    }));
  }
}

Context Cues (Metadata Filtering):

  • File path: Filter by module/folder (e.g., "frontend", "backend")
  • Timestamp: Sort/filter by recency when query implies "recent"
  • Kind: Filter by function/class/interface type
  • Module name: Match against known project modules

Phase 5 — Memory Architecture

5.1

Working Memory (In-Memory)

What it holds: Current conversation state — the active user query, the last N turns, current context snippets, active tool results.

// src/memory/WorkingMemory.ts
export class WorkingMemory {
  private turns: Message[] = [];
  private maxTurns: number = 20;   // Limit to avoid token overflow

  addTurn(message: Message): void {
    this.turns.push(message);
    if (this.turns.length > this.maxTurns) {
      this.turns.shift(); // Evict oldest
    }
  }

  getRecentTurns(count: number = 10): Message[] {
    return this.turns.slice(-count);
  }

  clear(): void {
    this.turns = [];
  }
}

Working Memory is NOT persisted. It lives only during the agent session. When the CLI exits, it's gone — unless key moments were saved to episodic memory.

5.2

Episodic Memory (SQLite)

What it holds: Structured records of important events across sessions — tool calls made, files modified, decisions taken, errors encountered.

You don't store every LLM response. You distill interactions into structured entries at the moment they happen.

// src/memory/EpisodicMemory.ts
import Database from 'better-sqlite3';

export class EpisodicMemory {
  private db: Database.Database;

  constructor(dbPath: string) {
    this.db = new Database(dbPath);
    this.db.exec(`
      CREATE TABLE IF NOT EXISTS episodes (
        id TEXT PRIMARY KEY,
        timestamp INTEGER NOT NULL,
        type TEXT NOT NULL CHECK(type IN ('tool_call','decision','observation','error','file_change')),
        summary TEXT NOT NULL,
        details TEXT   -- JSON blob for extra data
      )
    `);
  }

  async add(entry: EpisodicEntry): Promise<void> {
    this.db.prepare(
      'INSERT INTO episodes (id, timestamp, type, summary, details) VALUES (?, ?, ?, ?, ?)'
    ).run(entry.id, entry.timestamp, entry.type, entry.summary,
          entry.details ? JSON.stringify(entry.details) : null);
  }

  async getRecent(limit: number = 20, types?: string[]): Promise<EpisodicEntry[]> {
    let query = 'SELECT * FROM episodes';
    if (types?.length) {
      query += ` WHERE type IN (${types.map(() => '?').join(',')})`;
    }
    query += ' ORDER BY timestamp DESC LIMIT ?';

    return this.db.prepare(query).all(...(types || []), limit) as EpisodicEntry[];
  }

  async pruneOlderThan(timestamp: number): Promise<void> {
    this.db.prepare('DELETE FROM episodes WHERE timestamp < ?').run(timestamp);
  }
}

// Event structure for what gets stored:
// { type: 'tool_call', summary: 'read_file: src/index.ts', details: { success: true, linesRead: 50 } }
// { type: 'decision', summary: 'Selected OpenAIModel for this session', details: { model: 'gpt-4' } }
// { type: 'file_change', summary: 'Modified src/agent/AgentLoop.ts', details: { diff: '...' } }

Key Design Decisions:

  • Don't store raw LLM responses — they're verbose. Store summaries and outcomes.
  • Log as you go — when a tool call completes, immediately save a structured entry. No post-hoc LLM summarization needed.
  • Prune periodically — old episodes get archived/deleted to keep the DB lean.

Phase 6 — Guardrails & Error Handling

6.1

Pre-Call Validation

Before executing any tool, validate inputs to catch malformed or dangerous requests.

// src/guardrails/PreCallValidator.ts
export class PreCallValidator {
  validate(tool: Tool, args: Record<string, unknown>): void {
    // 1. Required parameters check
    for (const [name, param] of Object.entries(tool.parameters)) {
      if (param.required && args[name] === undefined) {
        throw new Error(`Missing required parameter: ${name}`);
      }
    }

    // 2. Type validation
    for (const [name, value] of Object.entries(args)) {
      const schema = tool.parameters[name];
      if (schema && typeof value !== schema.type) {
        throw new Error(`Parameter "${name}" expected ${schema.type}, got ${typeof value}`);
      }
    }

    // 3. Security: No path traversal
    if (args.path && typeof args.path === 'string') {
      if (args.path.includes('..') || args.path.startsWith('/')) {
        throw new Error('Path traversal detected: access denied');
      }
    }

    // 4. Size limits on inputs
    if (args.command && typeof args.command === 'string' && args.command.length > 1000) {
      throw new Error('Command too long (max 1000 characters)');
    }
  }
}
6.2

Post-Call Validation

After tool execution, validate the output before feeding it back to the LLM.

// src/guardrails/PostCallValidator.ts
export class PostCallValidator {
  validate(result: ToolResult): void {
    // 1. Output size check
    if (result.data && typeof result.data === 'string') {
      if (result.data.length > 1024 * 100) { // 100KB
        result.data = result.data.slice(0, 1024 * 100) + '\n... [truncated]';
        result.truncated = true;
      }
    }

    // 2. Sensitive data detection (basic)
    if (result.data && typeof result.data === 'string') {
      const sensitivePatterns = [
        /-----BEGIN (RSA|EC|OPENSSH) PRIVATE KEY-----/,
        /sk-[a-zA-Z0-9]{20,}/,   // OpenAI API key pattern
        /ghp_[a-zA-Z0-9]{36}/,    // GitHub token pattern
        /(?:https?:\/\/)?[^\s]+\.(?:env|pem|key)\b/,
      ];
      for (const pattern of sensitivePatterns) {
        if (pattern.test(result.data)) {
          result.data = '[SENSITIVE DATA REDACTED]';
          break;
        }
      }
    }

    // 3. Error detection (stderr always captured)
    // Already handled by ToolExecutor
  }
}
6.3

Output Guardrails

Validate the LLM's response before acting on it.

// src/guardrails/OutputGuard.ts
export class OutputGuard {
  check(response: LLMResponse): GuardResult {
    const issues: string[] = [];

    // 1. JSON parseable?
    if (!this.isValidJson(response)) {
      issues.push('Response is not valid JSON');
    }

    // 2. Tool exists?
    if (response.type === 'tool_call') {
      if (!this.toolRegistry.has(response.tool)) {
        issues.push(`Tool "${response.tool}" does not exist`);
      }

      // 3. Arguments match schema?
      const tool = this.toolRegistry.get(response.tool);
      for (const key of Object.keys(response.arguments)) {
        if (!tool.parameters[key]) {
          issues.push(`Unknown parameter "${key}" for tool "${response.tool}"`);
        }
      }
    }

    // 4. Content safety (no code injection via prompt)
    if (typeof response.content === 'string') {
      if (this.containsInjectionPatterns(response.content)) {
        issues.push('Response contains potential injection patterns');
      }
    }

    return { valid: issues.length === 0, issues };
  }
}

Phase 7 — Edge Cases & Their Handling

7.1 Infinite Loops / Runaway Processes

Scenario: LLM asks to run node run.ts where run.ts has an infinite loop (while(true) {}).

Handling:

  • Timeouts on every tool call — AbortController-based timeout on child_process. Default: 30s.
  • Configurable per tool — file reads can have shorter timeout (5s), shell commands longer (60s).
  • Process tree kill — ensure child and all its sub-processes are killed on timeout.
// Kill entire process tree on timeout
import { execSync } from 'child_process';

function killProcessTree(pid: number) {
  try {
    execSync(`kill -- -$(ps -o pgid= -p ${pid} | tr -d ' ')`, { timeout: 2000 });
  } catch {
    process.kill(pid, 'SIGKILL'); // Force kill
  }
}

7.2 Excessive Output from Tools

Scenario: A tool (e.g., running a test suite or cat'ing a large file) prints megabytes of data to stdout.

Handling:

  • Output byte limit: Cap at 1MB by default. Use maxBuffer option in exec.
  • Streaming truncation: For long-running output, stream chunk by chunk and stop after limit.
  • Flag as truncated: Set truncated: true in ToolResult so the LLM knows it didn't get full output.
  • Summary mode: For very large outputs, prepend a summary: "[Output truncated at 1MB. First 100 lines shown...]"

7.3 Malicious Code Execution

Scenario: User's project contains malicious code, or the LLM is prompted to run dangerous commands (rm -rf /, curl | bash).

Handling:

  • Command whitelist: Only allow safe commands (ls, cat, grep, find, node, npm, git). Block shell pipes |, redirects >, rm, sudo, curl, wget.
  • Path restriction: Limit file operations to the project directory. Block .. and absolute paths above project root.
  • Read-only by default: File reads are allowed by default. Writes require explicit user confirmation.
  • Docker sandbox (future): For full isolation, run each tool in a disposable Docker container.

7.4 Stale Embeddings / File Changes

Scenario: User modifies a file. The vector DB still has old embeddings, so context retrieval returns outdated code.

Handling:

  • File watcher: Use chokidar to detect file saves. On change, re-parse that file, re-embed changed functions, update by ID.
  • Hash-based change detection: Store a hash of each chunk's code. Only re-embed if hash changed.
  • Startup sync: On CLI launch, check all file modification timestamps and re-index any changed files.
  • Graceful fallback: If vector DB is stale, also do a fresh file read before feeding context to LLM.

7.5 LLM Returns Irrelevant Responses

Scenario: LLM goes off-topic, calls wrong tools, or gives nonsensical code suggestions.

Handling:

  • Structured output schema: Force JSON with response_format (OpenAI) or structured tool use (Anthropic).
  • Validate tool existence: Before executing, check the tool is registered. If not, respond with available tools list.
  • Lint/syntax check: Before applying code suggestions, run TypeScript compiler check on the proposed code.
  • Clarity check: If response is vague, auto-prompt: "Please be more specific about which file and what change."
  • Max retries: Limit the loop to N iterations (e.g., 15 tool calls max) to prevent infinite agent loops.

7.6 User Input Variability (Synonyms & Fuzzy Queries)

Scenario: User says "fix the recent bug in the UI" — how does the system know "recent" means "last modified"?

Handling:

  • Semantic matching: The word "recent" gets embedded and its vector is close to "new", "latest", "last". Embedding captures the meaning.
  • Metadata filtering: When query meaning relates to time, apply timestamp-based sorting/filtering in the retrieval step.
  • Your code interprets: After retrieving semantic results, your code checks if the query implies time-based filtering and applies it. No LLM needed for this step.
  • Combined approach: Semantic similarity finds what is relevant. Metadata filtering refines which specific item is relevant.

7.7 Large Conversation History

Scenario: After 50+ turns, the conversation history is too large for the LLM context window.

Handling:

  • Sliding window: Only keep the last N turns (e.g., 10-20) in working memory.
  • Episodic summarization: Store key outcomes in SQLite (not raw responses). Retrieve relevant episodes when needed.
  • Token budget: Track token usage per turn. When approaching limit, summarize old turns into a single system message.
  • Structured summary: "Earlier in the conversation: modified X file, ran Y tool, decided on Z approach."
